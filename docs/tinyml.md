# TinyML: DSP + ML co-design

## Why features, not raw samples

A raw-waveform CNN would see 2048 samples × 2 channels every 100 ms, which means tens of kilobytes of activations and millions of MACs. Here the DSP does the heavy lifting once, and hands the network **14 numbers**. The result:

| | this design |
|---|---|
| model | MLP 14 → 32 → 16 → 8 (ReLU, softmax), **1,144 parameters** |
| flash | **5,160 B** int8 flatbuffer |
| tensor arena | 4,096 B reserved on the MCU. Measured use is 1,936 B on the 64-bit host; the MCU reports its own value with `MODEL` |
| inference | 1.4 µs `Invoke()` on the host PC. On the Pico, `MODEL` / `BENCH` report `max_inference_us` and `ml_invoke`, measured on target |

## Feature vector (exact order — `firmware/src/features/feature_spec.h`)

| # | name | definition |
|---|---|---|
| 0 | `vrms_pu` | cycle-synchronous true RMS over the window / V_nom |
| 1 | `vmin_pu` | minimum Urms(½) in the window / V_nom |
| 2 | `vmax_pu` | maximum Urms(½) in the window / V_nom |
| 3 | `y_step` | (max − min)/mean of the load admittance Irms/Vpu over the window's half cycles |
| 4 | `freq_dev_hz` | f − f_nom (0 when invalid) |
| 5 | `thd_v_pct` | voltage THD % (0 when there is no valid fundamental) |
| 6 | `h3_pct` | H3/H1 % |
| 7 | `h5_pct` | H5/H1 % |
| 8 | `h7_pct` | H7/H1 % |
| 9 | `crest_factor` | peak \|v\| / Vrms |
| 10 | `kurtosis` | kurtosis of the window's samples (1.5 for a pure sine) |
| 11 | `peak_pu` | peak \|v\| / (√2·V_nom) |
| 12 | `wavelet_energy_log` | log10(Σ detail² / Σ v²) |
| 13 | `transient_energy_log` | log10(Σ cycle-deviation² / Σ v²), excluding echo regions |

**One definition, three uses.** An X-macro list generates the extractor order, the CSV header written by `pq_datagen`, and the names stored in the model header. The FNV-1a hash of the joined names (currently `0x7D4E6482`) is embedded in `model_data.h`. `Classifier_Init()` refuses any model whose hash differs from the firmware's, and flags `ML_INIT`; the DSP keeps working. Training order, conversion order and embedded order therefore cannot drift silently.

Standardisation (mean and standard deviation per feature, computed on training data) is also exported into `model_data.cpp` and applied in `Classifier_Run()` before int8 quantisation.

## Classes (model outputs)

`NORMAL, SAG, SWELL, INTERRUPTION, HARMONIC, TRANSIENT, FREQUENCY_VARIATION, LOAD_SWITCHING`. These are indices 0–7 of `PqClass`. `COMBINED_EVENT` is produced by fusion, not by the model.

## Training data: generated BY the firmware

`pq_datagen` renders random but physically plausible clips, 8 classes × N:

- background THD 0–5 %, noise 0.02–0.8 V;
- ±0.3 Hz frequency offset, 0.95–1.05 pu level;
- random ADC offsets of ±3000 counts (uncalibrated);
- load current 0.5–15 A with its own harmonics and a PF angle;
- one disturbance per clip: sags 0.12–0.86 pu with optional phase jump, swells 1.14–1.6 pu, interruptions, harmonic distortion at THD 10–32 %, impulsive and oscillatory transients, ramped frequency deviations of 0.75–3 Hz, and load steps of ×1.6–5 or ×0.15–0.55.

Each clip goes through the **actual** `SimAdcBackend → Calibrator → PqEngine` code, and one row is written per analysis frame. Frames whose window only partially overlaps a disturbance edge are labelled ambiguous and skipped.

## Training (`ml/train_model.py`)

- The validation split is **by clip**, because frames of the same clip are correlated.
- Class-balanced weights, Adam, early stopping.
- Full-integer post-training quantisation, with int8 input and output and a representative dataset.
- The **int8** model is evaluated with the TFLite interpreter on an independent test set (different seed).
- Export writes `model_data.{h,cpp}` with 16 reference vectors. The host test `ml.reference_vectors_match_training_output` checks that TFLM in the firmware returns **bit-identical** int8 outputs to the Python interpreter.

### Results of the shipped model (simulated test set, 18,217 frames, 2,400 clips)

| | frame accuracy |
|---|---|
| float Keras model | 99.90 % |
| **int8 TFLite model (what runs on the MCU)** | **99.90 %** (int8 vs float agreement 99.97 %) |
| DSP threshold rules alone, same frames | 98.45 % |

The ML is mainly strongest on **transients** (99.6 % vs 81.4 % frame recall for the rules; see fusion below) and on **normal vs load-switching** frames.

> **Important:** these numbers come from simulated waveforms produced by the same waveform model family used for training. They show that the pipeline and quantisation work, **not** field accuracy. Before relying on the model, record real disturbances with `tools/data_logger.py`, label them, and retrain or validate.

## Decision fusion (`fusion/decision_fusion.cpp`)

For each class c, `fused_c = α·e_c(DSP) + (1−α)·p_c(ML)`, with α = `fusion.dsp_weight` = 0.6, or 1 when ML is off. `e_c` is a soft DSP evidence value in 0..1, where 0.5 means exactly at the threshold.

The rules are applied in order:

1. **Standard-defined events are authoritative.** If the DSP state machines assert conditions (thresholds crossed with hysteresis), the final class is chosen only among them, ranked by the fused score. ML can re-rank but never veto, for example a sag that ML thinks is normal.
2. Asserted conditions from ≥ 2 families (voltage level, waveform, frequency, transient, load) give `COMBINED_EVENT`.
3. **Corroboration.** If nothing is asserted but the best non-normal fused score is ≥ 0.5 **and** the DSP has some evidence (> 0), that class is taken, with source `dsp+ml`. Example: a transient still inside its verification cycle, where e = 0.4 and ML says 0.99, gives fused 0.64 and a TRANSIENT decision one frame earlier.
4. **ML-only advisory.** ML predicts a non-normal class with ≥ 0.90 confidence for 3 consecutive frames, with no DSP evidence. This produces an event flagged `ML_ONLY_ADVISORY`. It is logged and reported but never drives control outputs.
5. Otherwise the result is NORMAL. Disagreement (ML > 0.8 on a class the DSP does not assert) is flagged `ML_DISAGREE` for model monitoring.

Examples from the specification, behaving as described:

- THD = 12 % (asserted) and ML HARMONIC = 0.96 give `HARMONIC_DISTORTION`, with fused 0.6·1 + 0.4·0.96 = 0.98.
- V = 0.78 pu (asserted) and ML SAG = 0.94 give `VOLTAGE_SAG`.

On the independent evaluation (`pq_datagen --eval --clips 150 --seed 4242`), frame-level accuracy is 98.56 % for DSP rules only, 99.90 % for TinyML only and 99.18 % for the fused output. Fusion follows the standard-defined DSP decision wherever it asserts, which is the intended trade-off. Event level:

| class | detected | clips with an unrelated extra event | mean detection latency |
|---|---|---|---|
| NORMAL | no events 100 % | 0 % | – |
| SAG / SWELL / INTERRUPTION | 100 % | 0 / 0 / 1.3 % | 12.7 / 12.4 / 12.7 ms |
| HARMONIC | 100 % | 3.3 % | 207 ms (one analysis frame) |
| TRANSIENT | 99.3 % | 0.7 % | 2.5 ms |
| FREQUENCY_VARIATION | 100 % | 0 % | 206 ms |
| LOAD_SWITCHING | 100 % | 0 % | 12.3 ms |

The "extra" events are physically real rather than errors:

- In 5 harmonic clips the distorted RMS exceeded 1.10 pu, which is by definition a swell.
- In 2 interruption clips the voltage return produced a recovery transient.

Latency is measured from disturbance onset to event start, including the 5 ms block buffering.

## Memory management

- `tensor_arena` is `alignas(16) static uint8_t[PQ_TENSOR_ARENA_SIZE]`, 4096 B on the Pico, set with `-DPQ_TENSOR_ARENA_SIZE`. The interpreter itself is placement-constructed into static storage. There is no heap use.
- The op resolver registers only the 5 needed ops (FullyConnected, Softmax, Relu, Quantize, Dequantize).
- `MODEL` reports model bytes, arena reserved and used, spec hashes, run count and maximum inference time.
- **Important integration detail.** The pico-tflmicro port unconditionally enables an experimental dual-core matmul (`TF_LITE_PICO_MULTICORE`) that dispatches work to core 1 through the multicore FIFO. Core 1 is our real-time core, so `cmake/pq_tflm.cmake` compiles a patched copy of that file with the feature removed.
